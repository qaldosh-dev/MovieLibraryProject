# Movie Library — гайд по созданию каркаса

Для Бауыржана, Айгерім, Аяулым и Ниязбека.

Это согласованный план будущей работы. Задачи ниже ещё не созданы в GitHub, а описанные Kotlin-файлы ещё не добавлены в новый проект.

## 1. Что мы сейчас делаем

Вместе собираем рабочую основу Android-приложения на Kotlin и Jetpack Compose, похожую на наш черновик. Каждый создаёт свою часть, понимает её и отправляет через Pull Request.

В конце этапа должны работать:

- Каталог из шести заранее подготовленных фильмов с локальными постерами.
- Поиск по названию и фильтрация по жанру.
- Экран подробностей выбранного фильма.
- Добавление и удаление из общего избранного.
- Переходы между четырьмя экранами и возврат назад.
- MVVM: данные отдельно, состояние и логика отдельно, интерфейс отдельно.

Интернет, API, авторизация, база данных и сложные библиотеки для этого этапа не нужны. Избранное переживает поворот экрана благодаря ViewModel, но постоянное сохранение после завершения процесса пока не входит в задачу.

Каркас уже должен быть функциональным. Финальные постеры будут локальными, но красивое оформление, иконку приложения и дополнительные улучшения можно дорабатывать следующим этапом.

## 2. Четыре экрана и их владельцы

| Участник | Экран | Что пользователь делает |
| --- | --- | --- |
| Бауыржан | Каталог | Смотрит все фильмы, ищет по названию, открывает фильм, отмечает избранное |

Внизу приложения: Catalog, Genres, Favorites. Подробности открываются нажатием на фильм. Поиск находится в каталоге, отдельного экрана поиска нет.

### Состояние и действия

`MovieUiState` содержит:

- `movies: List<Movie>`;
- `genres: List<String>`;
- `searchQuery: String`;
- `selectedGenre: String?`, где `null` означает все жанры;
- `favoriteIds: Set<Int>`.

Вычисляемые свойства: `filteredMovies: List<Movie>` и `favoriteMovies: List<Movie>`.

Внешние функции `MovieViewModel`:

```kotlin
onSearchQueryChange(query: String)
onGenreSelected(genre: String?)
toggleFavorite(movieId: Int)
```

ViewModel хранит private MutableStateFlow и предоставляет read-only StateFlow. Один экземпляр создаётся над NavHost и используется всеми экранами.

Экран получает данные и callbacks через параметры. Экран не создаёт свой MovieRepository, отдельный список избранного или новый MovieViewModel. Экран не принимает NavController: навигацию выполняет общий код через callbacks.

### Интерфейсы компонентов, которые должны совпасть

Это согласованные сигнатуры для будущего кода, а не готовые реализации. Во всех файлах объявляйте эти функции с `@Composable` и добавляйте необходимые imports.

```kotlin
fun MovieCard(
    movie: Movie,
    isFavorite: Boolean,
    onMovieClick: () -> Unit,
    onFavoriteClick: () -> Unit,
    modifier: Modifier = Modifier
)

fun CatalogScreen(
    uiState: MovieUiState,
    onQueryChange: (String) -> Unit,
    onMovieClick: (Int) -> Unit,
    onFavoriteClick: (Int) -> Unit,
    onClearGenre: () -> Unit
)

fun DetailsScreen(
    movie: Movie?,
    isFavorite: Boolean,
    onFavoriteClick: () -> Unit
)

fun FavoritesScreen(
    movies: List<Movie>,
    onMovieClick: (Int) -> Unit,
    onFavoriteClick: (Int) -> Unit
)

fun GenresScreen(
    genres: List<String>,
    onGenreClick: (String) -> Unit
)
```

`MovieLibraryApp()` соединяет экраны, читает состояние через collectAsState и передаёт параметры.

Repository — `object MovieRepository` с `movies: List<Movie>`, `genres: List<String>` и `getMovieById(movieId: Int): Movie?`. Жанры получаем из фильмов через `map` и `distinct`, чтобы не хранить расходящиеся списки.

### Общие маршруты

| Маршрут | Назначение |
| --- | --- |
| catalog | Все фильмы |
| catalog?genre={genre} | Та же функция CatalogScreen с фильтром |
| genres | Выбор жанра |
| favorites | Избранное |
| details/{movieId} | Подробности, movieId имеет тип Int |

В NavHost каталог можно объявить одним маршрутом `catalog?genre={genre}` с необязательным nullable String-аргументом и значением по умолчанию null. Это один экран, не два.

Для жанра в URL используем `Uri.encode(genre)`. Нажатие фильма из каталога или избранного передаёт ID. Сценарий жанров: жанр → отфильтрованный каталог → подробности. Отдельные подробности из GenresScreen не нужны.

## 6. Порядок и зависимости

Задача считается разблокированной, когда её зависимости уже объединены в main. Просто чужой push или открытый PR ещё не означает готовность основы.

| Метка | Задача | Исполнитель | Нужен merge в main прежде чем сдавать |
| --- | --- | --- | --- |
| F01 | Зависимости ViewModel и Navigation Compose | Бауыржан | CI уже объединён |
| F02 | Модель Movie | Бауыржан | Нет зависимости от других задач каркаса |
| F03 | Шесть локальных постеров | Айгерім | Нет зависимости от других задач каркаса |
| F04 | MovieRepository | Ниязбек | F02 + F03 |
| F05 | Общая MovieCard | Аяулым | F02 + F03 |
| F06 | UI State и MovieViewModel | Бауыржан | F01 + F04 |
| F07 | DetailsScreen | Айгерім | F02 + F03 |
| F08 | GenresScreen | Ниязбек | F04 |
| F09 | FavoritesScreen | Аяулым | F05 |
| F10 | CatalogScreen | Бауыржан | F05 + F06 |
| F11 | NavHost и MovieLibraryApp | Ниязбек | F01 + F06 + F07 + F08 + F09 + F10 |
| F12 | Подключение к MainActivity и общая проверка | Бауыржан + все | F11 |

Начинаем параллельно: Бауыржан делает F01/F02, Айгерім — F03. Ниязбек в это время готовит описания и демонстрационные рейтинги шести фильмов по согласованной таблице; Аяулым разбирает договорённость MovieCard и готовит её макет. Эти подготовительные действия не требуют придумывать пустые коммиты.

После merge F02/F03 одновременно можно делать F04, F05 и F07. После F04 — F06 и F08. После F05 — F09. Затем F10, F11, F12.

Узкое место перед навигацией — готовность четырёх функций экранов. Бауыржан в первую очередь проверяет PR, от которых зависят другие. Не начинаем все части сразу через копирование чужих незавершённых веток.

Экран до подключения навигации проверяем через @Preview с примером данных и callbacks. Успешный Preview не заменяет проверку навигации и общей работы в F12. Не переписываем MainActivity в каждой ветке, чтобы временно подключить свой экран.

## 8. Как работать с веткой, коммитами и PR

Перед началом задачи текущая работа должна быть сохранена. Сначала проверить `git status`. Затем:

```powershell
git switch main
git pull --ff-only origin main
git switch -c feature/aigerim-details
```

Это пример: каждый использует имя ветки из своего Issue. Создаём ветку после merge её зависимостей и обновления main. Не создаём заранее все будущие ветки от старой версии.

Во время работы:

```powershell
git status
git add путь/к/своему/файлу
git commit -m "Add movie details layout"
git push -u origin feature/aigerim-details
```

Текст пути — пример, его нужно заменить реальным путём файла. После первого push достаточно `git push`.

Можно сделать несколько локальных коммитов и отправить одним push: отдельные коммиты сохранятся. Новая ветка не нужна после каждого push.

После push исполнитель открывает PR: base = main, compare = его ветка. Исправления замечаний отправляются в эту же ветку, PR обновляется автоматически. Сразу после первого рабочего результата можно открыть Draft PR; когда задача готова — Ready for review.

Шаблон описания PR:

```text
Closes #НОМЕР_ISSUE

Что сделано:
- ...

Изменённые файлы:
- ...

Как проверено:
- Сборка / Preview / unit-тесты / запуск на устройстве — указать фактически выполненное.

Что ещё не проверено:
- ...
```

Перед началом следующей задачи снова переключиться на main и выполнить pull. Если зависимость не объединена, сообщить об ожидании в Issue. Если во время долгой задачи main сильно изменилась, согласовать с Бауыржаном обычный merge origin/main в свою ветку; не применять force push и не переписывать чужую историю.

## 9. Правила проверки и коммитов

- В main объединяет Бауыржан. Остальные не обходят защиту.
- GitHub Actions автоматически собирает APK, запускает unit-тесты и Android Lint. Это не проверка всех нажатий и внешнего вида.
- Зелёный CI сам по себе не означает, что сценарий на устройстве выполнен.
- Каждый перед PR проверяет свою часть. Бауыржан проверяет изменённые файлы, CI и критерии Issue.
- Не заявлять о проверках, которые не выполнялись. Для неподключённого экрана честно писать «сборка и Preview; интеграционный сценарий ожидает F12».
- Минимум 10 содержательных коммитов каждому — требование всего проекта. Эти 12 задач не являются планом «получить все коммиты на каркасе».
- Коммит фиксирует реальное изменение. Не добавлять пустые коммиты и не делить строки ради счётчика.
- После каркаса останутся оформление, доступность, иконка, адаптация и исправления по тестированию: их отдельно распределим.
- Merge выполняем через Create a merge commit, чтобы сохранить коммиты исполнителя. Не использовать squash.
- Каждый должен понимать собственный код. Если помогает ИИ, дать ему только своё Issue, договорённости из раздела 4 и актуальные зависимости; не просить написать всё приложение.
